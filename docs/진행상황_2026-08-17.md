# LLM Hallucination 연구 프로젝트 — 진행상황 정리 (2026-08-17)

Claude 웹에서 "제출용 앱을 어떻게 만들지" 논의하기 위해 현재까지의 상황을 정리한 문서입니다.

## 1. 연구 배경 (2026.7 방향 전환됨)

원래는 "검증 시스템 앱 개발"이 목표였으나, **"실험 + 논문"**으로 무게중심이 바뀌었습니다. UI(app.py) 개발은 보류 상태였습니다.

**연구 질문**: RAG는 정확도를 높이지만, 검색이 잘못된 근거를 가져왔을 때 LLM이 그걸 신뢰해 오히려 더 위험한 답변을 만들 수 있습니다. 항만 안전 도메인에서 이 취약성을 정량화하고, 기권 유도 프롬프트가 이를 완화하는지 검증합니다.

**일정**: 8월 실험 파이프라인 완성 + 본 실험 → 9월 분석 + 논문 초안 → 10월 중순 논문·발표 마감 (10/21 중간고사 전)

## 2. 실험 설계

### 5개 조건

| 조건 | 근거 | 지시문 |
|---|---|---|
| A | 없음 | 기본 |
| B | 정상 top-k | 기본 |
| B_dirty | **오염** | 기본 |
| C | 정상 top-k | 기권 유도 |
| C_dirty | **오염** | 기권 유도 |

핵심 비교는 **B_dirty vs C_dirty** — 오염된 근거를 받았을 때 기권 유도 지시문이 방어해주는지가 이 연구의 결론입니다.

### 오염 근거의 정의
"부산항 질문에 인천항 문서를 근거로 주입"하는 방식. port 메타데이터로 다른 항구 문서만 골라 제공하며, **공통 문서는 오염이 아님**(전국 규정이라 모든 항구에 정당하게 적용됨). 오염 검색 조건: `port != 질문항구 AND port != "공통"`.

### 측정 지표 — 3분류
정답 / **기권**("자료에 없습니다") / **오답**(틀린 내용 단정). 2분류가 아니라 3분류인 이유는, 항만 안전에서 "모른다"(안전한 실패)와 "틀린 답"(위험한 실패)이 전혀 다르기 때문입니다. 오답이 기권으로 전환되는 것이 이 연구의 핵심 결과입니다.

### 기술 스택 (변경 금지)
- ChromaDB 직접 사용 (LangChain 프레임워크는 청킹 함수만 부분 사용)
- sentence-transformers `jhgan/ko-sroberta-multitask` (한국어 임베딩)
- gpt-4o-mini, **temperature 0.7 고정** (반복 실험의 전제)
- 답변 생성과 판정을 완전히 분리 (판정은 별도 세션, judge.py가 담당, 정답 근거는 답변 생성 프롬프트에 절대 노출 안 함)

## 3. 파이프라인 구현 현황

| 파일 | 상태 | 설명 |
|---|---|---|
| `data_prep.py` | ✅ | PDF/마크다운 → 정제 → 청킹(청크 500자, 겹침 50자) → 임베딩 → ChromaDB. port 메타데이터, 별표/별지 섹션 분리 및 상호 참조 연결까지 구현됨 |
| `llm.py` | ✅ | `get_llm_answer(question, context, abstain_instruction)` — gpt-4o-mini 호출, 기권 유도 지시문 on/off 지원 |
| `search.py` | ✅ | `search_normal`(정상 검색), `search_contaminated`(오염 검색, 다른 항구 문서만 선택). 검색 결과에 별표/별지 참조 자동 연결 |
| `experiment.py` | ✅ | 5개 조건별 프롬프트 조립 + 반복 실행 + CSV 저장. CLI로 top_k/조건/반복횟수 조정 가능 |
| `judge.py` | ✅ | LLM-as-a-Judge(gpt-4o-mini, temperature=0)로 정답/기권/오답 자동 판정. 답변 생성과 완전히 분리된 별도 세션 |
| `analyze.py` | ✅ | judge.py 결과 CSV를 모아 조건별 정답/기권/오답 비율 집계, Wilson 신뢰구간 계산 |
| `lab.py` | ✅ | 팀원용 내부 테스트 Streamlit 도구 (조건별 답변 실행 / 검색결과만 보기 / 판정 테스트, 3탭 구성). **제출용이 아님**, 실험 파라미터를 그대로 노출하는 개발용 도구 |
| `app.py` | ⚠️ 빈 껍데기 | 8줄짜리 스텁. 연구 방향 전환 전 "Safe/Warning/High Risk" 프레이밍의 잔재만 남아있고 실질적 기능 없음. **오늘 논의하려는 "제출용 앱"이 이 자리를 대체하거나 새로 만들 대상** |

파이프라인 자체는 end-to-end로 동작 확인됨 (`test_judged.csv`에 실제 조건별 판정 결과 존재 — 예: "정기안전점검은 얼마나 자주 실시해야 하나요?" 질문에 B/C 조건 모두 "정답"으로 판정된 사례).

## 4. 오늘(8/17) 진행한 작업 — 문서 전처리

RAG 근거로 쓸 원본 PDF들을 `data_prep.py`가 잘 청킹할 수 있도록 두 문서를 정제했습니다.

### 4-1. 공통_안전규정_한국항만연수원_항만하역통합안전매뉴얼
- 표지(1p)·목차(7p) 제거
- 문서 내부 페이지 114~123(8.9.2~8.9.6절, 하역작업 단계별 절차 34단계 + 흐름도 3개)이 완전히 그림으로만 되어있어 텍스트 추출이 거의 0이었던 것을 확인, 해당 페이지들을 PDF에서 제거
- 위 34단계 절차 + 흐름도 3개, 그리고 문서 전체를 훑어 추가로 찾은 5개 그림(PPE 종류, 현문사다리 규격, 와이어로프 결함 종류, TBM 5단계, IMDG 픽토그램+옥외저장소 이격거리)을 수기로 전사해 별도 보충 마크다운(`_보충자료_정제.md`)으로 작성
- 원본은 `documents/_raw/`에 백업
- 결과: 본문 PDF(146p) 310청크 + 보충자료 30청크 = 340청크

### 4-2. 울산항_안전규정_울산항만공사_일반화물안전매뉴얼 (신규 추가)
- 표지·발간사·목차·각 장 사이 표지/여백 페이지(10개 장×2p)·판권 페이지 제거 (215p → 185p)
- 이 문서는 "위험요인/안전표준작업" 내용이 실제 텍스트로 박스에 들어있고 사진은 참고용이라, 그림에 텍스트가 갇혀 인식 안 되는 구간이 없었음 (전체 페이지를 표본 검토해 확인) → 보충 마크다운 불필요
- 파일명에 `_정제` 접미사가 없어 트림 후 명명규칙에 맞게 리네임
- 결과: 243청크, port=울산항으로 정상 분류

## 5. 아직 안 된 것 / 열린 이슈

- **본 실험 미실시**: `experiment.py`는 동작하지만, 지금까지는 소규모 스모크 테스트(`results/smoke_test.csv`, `test_judged.csv`)만 있고 본 실험(5조건 × 전체 질문 × repeats)은 아직 안 돌림
- **`항만_질문_초안.md`가 현재 `documents/`와 안 맞을 수 있음**: 초안의 참고 문서명(`접안_안전관리지침_BPA.pdf` 등)이 실제 `documents/` 파일명과 다름 — 질문 세트를 현재 문서 구성에 맞게 재검토 필요
- **제출용 앱(`app.py`) 설계 미정**: 오늘 논의하려던 주제. 후보로 논의 중이던 옵션:
  1. **하이브리드(추천)**: 핵심 결과(B_dirty vs C_dirty 등)는 미리 돌린 CSV로 안정적인 대시보드로 보여주고, 그 옆에 "직접 질문해보기" 라이브 탭을 곁들임
  2. **라이브 데모**: 평가자가 질문을 입력하면 그 자리에서 조건별로 LLM을 호출해 답변을 보여줌 — 인터랙티브하지만 발표 중 API 지연/실패, temperature=0.7로 인한 답변 재현성 문제 리스크
  3. **결과 대시보드만**: 이미 돌린 실험 결과 CSV를 시각화만 — 안정적이고 논문 수치와 정확히 일치하지만 정적임
  - `lab.py`가 이미 라이브 실행 로직(조건별 답변 실행, 검색결과 보기, 판정 테스트)을 갖추고 있어서, 재사용 가능성이 있음. 다만 lab.py는 top_k 슬라이더·포트 텍스트입력 등 실험 파라미터를 그대로 노출하는 "내부 개발자용" 화면이라, 제출용으로 쓰려면 평가자 대상으로 다듬어진 화면이 필요함
